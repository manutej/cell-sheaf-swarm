Cell-Sheaf unification ideation

date: 2026-10-04 · topic: cell-sheaf-unification · focus: two-repo overlap, MVP product, federated loops · mode: repo-grounded

Grounding context

cell-sheaf is the copy-paste HTML design template (Pages, no TS). cell-sheaf-swarm is the contract kernel: JSON Schema, validate CLI, Zustand swarm clock, React observatory sources, CI. READMEs cross-link; template/ and contracts mostly overlap but swarm is canonical (schema, ROLL, adp specimen). The swarm contract already models the desired architecture: orchestrator, multi-agent-eval, broken lattice-ops ρ, operad compose≟collapse, JEV 128 — but React was not runnable until observatory/.

EVAL.md adversarial read: users need a verdict sentence, not ρ counts; operators need ranked repairs; federation addresses orchestrator/eval stress without restyling tokens.

Topic axes

  1. Repo & publish topology (two remotes vs monorepo vs npm package)
  2. Runtime surfaces (static template vs React observatory vs CLI harness)
  3. Running loops & evaluation (pulse, federation, meta-learning)
  4. Contract lifecycle (ROLL, validate, catalog, repair law)
  5. Product narrative (MVP persona, metrics, 10× leap from idea)

Ranked ideas

1. Kernel-first monorepo with publish mirror 2. Federated loop as CI gate 3. Shared insight bundle for HTML + TS 4. Observatory-as-product, template-as-top-of-funnel 5. Meta-learning wiki (noether-wiki pillar) 6. Real lattice-ops bridge (fix r-op) 7. Spec-to-Notion implementation tracker

1. Kernel-first monorepo with publish mirror

axis: repo topology · confidence 82% · complexity M

Keep cell-sheaf-swarm as sole writeable kernel; cell-sheaf becomes a release mirror of template/ + catalog only, updated by tag sync job.

direct: README.md (both repos) — "Copy template/" and cross-links; diff shows swarm owns sheaf-graph.schema.json

Rationale: Stops tokens.css drift (already differ slightly). Preserves zero-install Pages audience.

Downsides: Two remotes until merge; sync discipline required.

2. Federated loop as CI gate

axis: running loops · confidence 78% · complexity M

Run npm run federation:run in CI after validate; fail only on schema, warn on eval seats until specimen repaired.

direct: scripts/federated-harness.mjs — three cells, four-seat eval, meta-learning jsonl

Rationale: Encodes operad/JEV story as executable law, not demo animation.

Downsides: Flaky if stochastic pulse; may need seeded RNG.

3. Shared insight bundle for HTML + TS

axis: runtime surfaces · confidence 70% · complexity H

Build insight.ts to small ESM via esbuild; import from volume.boot.js for identical repair ranking on Pages.

direct: contracts/EVAL.md + src/lib/swarm/insight.ts — verdict/repairs already in TS, boot.js still header counts

Rationale: Closes P0 "views are a costume" by one ranking law everywhere.

Downsides: Introduces build step to "no build" template philosophy.

4. Observatory-as-product, template-as-top-of-funnel

axis: product narrative · confidence 85% · complexity M

Ship Vite observatory for operators; keep static template for designers rolling sheaves. Single STRATEGY.md names both tracks.

reasoned: STRATEGY tracks + swarm six modes vs template six design views — complementary, not duplicate SKUs

Rationale: 10× vs "idea" = runnable loop + readable volume, not more JSON fields.

Downsides: Two UX surfaces to maintain.

5. Meta-learning wiki (noether-wiki pillar)

axis: running loops · confidence 65% · complexity H

Persist federation.jsonl into rolling sheaf commits on wiki pillar; export rolls session warm.

direct: swarm.sheaf.json — wiki pillar + missing r-tw; agent p2 task "fold session warm"

Rationale: Makes meta-learning visible in-contract, not hidden dotfile.

Downsides: Contract bloat; needs ROLL rules for artifacts.

6. Real lattice-ops bridge (fix r-op)

axis: contract lifecycle · confidence 88% · complexity L

Repair broken orchestrator→lattice-ops ρ in specimen or emit sidecar ops dashboard that satisfies type-aware embed law.

direct: insight.ts repairs — fix orchestrator→lattice-ops opens lattice-ops; EVAL counterfactual

Rationale: MVP credibility: federation currently blocks 5 agents — product demo must show path to green.

Downsides: May require real external integration definition.

7. Spec-to-Notion implementation tracker

axis: product narrative · confidence 60% · complexity L

Mirror unified plan U-IDs to Notion tasks for stakeholders; link PRs back to sheaf commits.

external: spec-to-implementation skill — plan phases map to task DB rows

Rationale: Bridges math-native repo to delivery hygiene without issue-tracker in sheaf.

Downsides: Second system of record if not kept sparse.
